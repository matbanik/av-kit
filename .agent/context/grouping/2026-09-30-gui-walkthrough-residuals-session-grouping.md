## 3. Recommended grouping — 5 sessions

### Session 27 — `tts-repair` (MEU-62, MEU-63, MEU-64) · P2

- **Layer / files:** `packages/core` `services/tts.py`, `services/models.py`, `services/health.py`; `packages/infrastructure` `tts/adapter.py`, `model_manager/`; `packages/api` `wiring.py`, health/models schemas + OpenAPI diff; `ui/src/renderer/src/features/tts/*`; Settings Dependencies card rows.
- **Why grouped:** the engine repair (MEU-62) is the only item that makes TTS produce audio again, and the two page MEUs cannot be verified end to end without it — a `Failed` chip proves nothing until generation works. The three MEUs share `TTSPage.tsx`, its behaviour test and one Electron wave; reading the page once and running one wave beats three sessions. MEU-64 has no dependency on MEU-62 but reopening `TTSPage.tsx` in a later session would repeat the comprehension cost.
- **Order inside the session:** MEU-62 first (its readiness rows are consumed by MEU-63), then MEU-63, then MEU-64.
- **Cloud/local:** MEU-62's Python work runs fully in the container (pytest, contract tests) except the real Kokoro download; the authoritative gate and the "does audio come out" check are the local stage. Plan the `human-gate-decision.md`, the env-bound census and the reviewer route at plan time per `cloud-local-collaboration.md` §1.
- **Token estimate:** calibrate vs Session 24 `p11-queue-pages` (three MEUs, one page family, one wave) for the UI half plus `p9-capture-api-mcp` (MEU-37/38) for the Python + OpenAPI half.
- **Split flag:** **yes, candidate.** If the MEU-62 handoff lands past ~50% context, close the session as 27a and run MEU-63/64 as 27b from a fresh context; the boundary is clean because MEU-62 ships its own contract tests and readiness rows.

### Session 28 — `mcp-live-audit` (MEU-68) · P3

- **Layer / files:** `.agent/workflows/mcp-audit.md`, `.agent/skills/mcp-tool-audit/SKILL.md`, a runner under `mcp-server/scripts/` or `tools/`, `resources/baseline-snapshot.json`, `.agent/context/MCP/mcp-tool-audit-report.md`.
- **Why here:** it runs right after the TTS repair so its first baseline records a working `tts.generate`; run before the Capture sessions, it becomes the regression net for everything that follows (Session 30 adds two MCP actions the audit must then cover — that is a one-line baseline update, not a reopen).

Its Playwright-free nature makes it the cheapest local stage in this batch.
- **Token estimate:** calibrate vs Session 6 `p5-mcp-server` (MEU-18 compound tools) for the client/action surface and vs `p6-gui-settings-help` (MEU-23's gui-actions-index audit) for the audit tooling shape.
- **Split flag:** no.
