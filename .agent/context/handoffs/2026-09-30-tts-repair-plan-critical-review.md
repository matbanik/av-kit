## Intent Anchor

Executing this plan is supposed to make TTS produce audio again on Mat's machine (both Kokoro runtime assets — the `config.json` vocab and spaCy `en_core_web_sm` — become managed downloads with Dependencies readiness rows, `generate` fails fast with a 409 naming a missing asset, every `Failed` job carries an `error_message` and `tts.generate*` reaches the Console), then replace the hidden Manage grid with a picker plus one state-driven Get/Load/Unload button that also renders `job.error_message`, and finally add Apply cleanup, drop the raw preview and replace the language select + 236 px voice list with a searchable combobox so Speed and Format are visible at the default window — MEU-62 → MEU-63 → MEU-64, under the Sessions 25/26 cloud/local split with one authoritative `WINDOWS_GATE` plus a real-network `TTS_LIVE`.

Would executing this plan as written deliver that? Not as written. Three delivery-level defects stand in the way: the plan's proof that the Space rule can be observed (AC-64.6's Electron Red) cannot be produced because the E2E seam serves one voice, so the "Speed/Format visible" assertion passes on the unchanged layout and the deliverable is certified by a vacuous oracle (Finding 1); row 13's hub edit re-owns the TT rows to MEU-63/64 while `layout-canon.test.ts` AC-50.4 locks those cells to `MEU-5[2-8]` and the mockup's label/disposition, so the row's own `hub` predicate and the next full Vitest gate cannot both pass (Finding 2); and the single-statement contract `REQUIRED_TTS_ASSETS` misses the repository's own spaCy consumer (`services/prepare.py:_chunk`, default-on `chunk` step, every voice), so the fail-fast rule the plan would freeze into Red assertions and write into `03-service-layer.md` is wrong (Finding 3). Everything else — upstream research, the sha256 pin, the boundary inventory, the Out-of-Scope basis cells, the D-8–D-17 obviousness test, the `.ps1` against the `.sh` — was verified against sources and holds, with the Medium/Low notes below.
