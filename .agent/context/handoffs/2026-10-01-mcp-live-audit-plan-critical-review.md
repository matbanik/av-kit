## Intent Anchor

Executing this plan is supposed to deliver MEU-68: a TypeScript runner under `mcp-server/scripts/audit/` that spawns an isolated backend, launches the **built** MCP server over stdio with the `copyMcpConfig` env, drives all 67 actions of the 8 compound tools in dependency order, judges each step on an independently observed REST/filesystem state (never the envelope), proves every destructive action refuses without `confirm`, cleans up, and diffs a committed baseline; plus the `/mcp-audit` workflow, the `mcp-tool-audit` skill, a reconciled `05-mcp-server.md` §MCP live audit, and — after MEU-62 lands — the first authoritative Windows baseline and report, closed by independent execution review.

The verdict question is whether executing the plan as written would deliver that. It would not: Part A stalls at task row 3 because its `green` cell runs test files whose subjects are built only in rows 4, 5 and 7 (Finding 1); Part B can never start because the `SEQUENCING_GATE` script's predicate cannot match the output of the tool it reads (Finding 2); and the one container run that proves the runner against a real backend (row 6) depends on exactly the MEU-62 defect that H-3 was chosen to sidestep (Finding 3). The design itself — `OBSERVABLE_RULE`, `REFUSAL_ORACLE`, `ISOLATED_ROOT`/`ISOLATION_GUARD`, `DELTA`, `BASELINE_UPDATE_RULE`, the Windows gate exchange and its check — is sound and verified against sources below.
