## The one thing this round is really about

Adopting Zorivest's palette verbatim, under Zorivest's own pill rule (`bg-<token>/10
text-<token>` — the fill and the text are the SAME token, tinted 10%), produces a measured
result:

**28 of 80 status-pill / backdrop / theme pairings clear 4.5:1. 52 do not.** Light theme is
worst (`Paused` 2.23, `Done` 2.47). The baseline is in `contrast-matrix.json`.

The plan's position: this is *inherited* debt, not a regression av-kit introduces — those are
the values Zorivest ships today — and the only real remedy is repointing shared token **values**
app-wide (which is what Zorivest itself did once: `--color-accent-red: #ff5555 → #ffa0a0`,
commented "was #ff5555 @ 2.91:1"). That is neither queue-local nor an av-kit-local call. So
AC-42.3 gates on an exact-match measured baseline plus an exhaustive pass/debt partition plus a
required open `QUEUE-PILL-AA-DEBT` issue, rather than on a blanket ≥4.5 the chosen palette
cannot meet.

**Tell us whether that is the right call.** Concretely:

- Is shipping 52 sub-AA pairings acceptable for a local desktop tool, given the user's explicit
  instruction to use Zorivest's colour, or should the plan instead repoint the offending token
  values now and accept the app-wide blast radius?
- Is "one token for fill and foreground at 10% alpha" a defensible pill design at all, or is the
  honest answer that light theme needs a darker foreground and the lock should be read as
  "Zorivest's hues" rather than "Zorivest's classes"?
- Does the pass/debt partition actually prevent laundering, or can a future agent move a pairing
  from debt to pass without the ratio improving?

Answer with a recommendation, not a survey.
