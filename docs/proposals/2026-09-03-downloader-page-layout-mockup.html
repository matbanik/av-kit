Downloader page: two zones instead of one column

Every control on the page today is a full-width sibling in a single stack. The primary task sits under three diagnostic buttons, a one-time setting is interleaved with per-download fields, and the queue controls are three blocks away from the queue. This mockup regroups the same controls by what the user is doing and changes nothing about what they do.

Zone 1 · AddPaste, pick quality, press Add. One panel: URL and Add on the same line, options underneath. Cookies and SABR fold into Advanced.
Zone 2 · QueueOne header row: select-all and live status chips on the left, the four-control toolbar on the right, directly above the cards it acts on.
WidthThe content column is capped (~1150px) and left-aligned. No select stretches to 1960px to hold “1080p”.
ScopeComposition only. Every test id and every reachable action survives; the inventory in §05 is the checklist.

  1. SABR diagnostics come first. Three buttons most users will never press are the first interactive thing on the page. They are session-level troubleshooting, not part of adding a download.
  2. The URL field is the whole page wide. A 3400px input for a URL is not more useful, and it pushes Add eight elements down and away from the field it belongs to.
  3. Selects stretch to fit the window, not the value. “1080p” in a 1960px select signals that nothing on the page was sized on purpose.
  4. A persisted setting sits among per-download fields. Cookie mode is saved on change and rarely revisited, yet it reads like something to fill in every time.
  5. Test Cookies has the same weight as Add. Both are full-width; the secondary action has no visual reason to be secondary.
  6. The hint points to a button five blocks away. “Click Start to download” appears at the top; Start is the last thing on the page.
  7. Empty is announced three times. “0 items”, the empty drop zone, and eight “: 0” counts carry the same information.
  8. Eight zeros. The summary lists every status regardless of count, so the one that matters (a failure) never stands out.
  9. Queue controls are below the summary. The actions that operate on the list are separated from it by the summary and the processor line, and end up at the bottom of the page.

03Why this shape

ProximityAdd sits on the URL line because Enter and the button do the same thing. The SABR chip sits next to Quality because SABR is a quality limit. Start sits above the cards because Start acts on the cards.
FrequencyEvery-time controls (URL, quality, audio) are always visible. Once-in-a-while controls (cookies, SABR) are one click away under Advanced, which remembers its open state for the session.
One primary action per zoneThe Add panel has one filled button. The queue header has one highlighted toolbar state (the active verb). Everything else is ghost or secondary.
Say it onceThe status chips replace the eight-count summary and only show non-zero statuses. Empty is said by the drop zone alone; the header just reads “0 items”.
Sized to the valueQuality and format selects are content-width. The URL field is the only element that grows, and only up to the column cap.
Feedback where the action was“Queued … · position 5” appears under the URL line, where the user's eye already is, instead of a paragraph that scrolls the page.
The two frames above differ only in data. Same DOM order, same components: HelpCard → add panel → QueueSelectionHeader + QueueToolbar in one row → BulkActionBar → QueueList. The change is composition inside DownloaderPage.tsx, plus a small optional slot on the selection header for the chips.

04Sizing and tokens

  • Column. The page root becomes flex h-full min-h-0 flex-col gap-4 p-4 w-full max-w-6xl (1152px), left-aligned inside the content area rather than centered in a 3400px window. h-full min-h-0 is a Phase 10 input (QUEUE_SCROLL_CONTAINER_RULE): without it dnd-kit's KeyboardSensor clamps against <main> and keyboard reorder never moves.
  • Queue scroller. download-queue-region is flex-1 min-h-[20rem]. overflow-auto lives on a wrapper around QueueList only — not on the shared list container, which is the file-drop overlay's containing block. Header, bulk bar and toast stay outside that scroller (USER_LOCKS lock 1).
  • Which pane yields. This column is oversubscribed at the app's own 1280×800 default window, so one pane has to give up height. It must not be the queue: at the flex default every child shrinks in proportion to its content and the queue lands at 92px, which re-arms the KeyboardSensor clamp one level below <main> and takes keyboard reorder back out. So the controls above the queue are one flex min-h-0 flex-col gap-4 overflow-auto pane that absorbs the whole deficit, the summary and toolbar sit in one flex shrink-0 flex-col gap-4 wrapper so they are not clipped in its place, and the min-h-[20rem] floor keeps the queue out of the negotiation entirely. Widening the column here does not repeal this — it is a vertical constraint, and any Phase 11 layout that reintroduces a shrinkable queue reintroduces the bug.
  • Controls. URL input and Add are md (h-9, 36px). Everything on the options row and in Advanced is sm (h-7, 28px). Toolbar buttons stay as they are. This is the frozen G34 scale; nothing new.
  • Panel. One rounded-lg border border-border with a faint elevated fill. It is the only bordered block on the page other than the help card and the cards themselves.
  • Chips. 22px pills using existing status tokens: accent-cyan downloading, accent-green done, error for failed / blocked / age-restricted, fg-muted for pending / skipped / cancelled, accent-orange for the SABR warning. No raw hex (G32).
  • Segmented cookie control. Still three <input type="radio" name="cookie-mode"> under the hood, styled as one grouped control. Keyboard behavior is the native radio group.
  • Motion. The Advanced disclosure and the live-dot pulse use duration-fast / ease-out and honor prefers-reduced-motion (G33).

06Decisions to lock before planning

  • Advanced default. Proposed: collapsed unless cookie mode ≠ none or SABR is active. Alternative: always collapsed. The first is friendlier; the second is simpler to test.
  • Status chips vs. the eight-count summary. Proposed: non-zero only. If a full census is wanted for support screenshots, the eight counts can live in the More menu as a read-only line, or as a tooltip on “n items”.
  • Convert page parity. The Convert page has the same single-column shape. This mockup is Downloader only, but the queue header row (Zone 2) is page-agnostic and should land on both pages in the same MEU so the two queues do not diverge again. The add panel is Downloader-specific.
  • SABR chip placement. Proposed: beside Quality, because that is what it constrains. Alternative: keep the full-width banner. The chip is quieter; the banner is louder. SABR being active is a degraded state, so there is an argument for loud, but the current banner also pushes the whole form down.

Fits the MEU-48/49 convergence window as a composition MEU. No API change, no new dependency, no new component beyond the disclosure wrapper.
