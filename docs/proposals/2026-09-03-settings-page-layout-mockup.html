Settings page: a rail, a form grid, and an honest save model

Settings is nine bordered boxes stacked in one column with every control stretched to full width. Some sections save as you type, two need a Save button, and one applies instantly, but nothing on the page says which is which. This mockup adds a sticky rail so any section is one click away, sets every section in the same label-and-control grid, gives paths their Browse button on the same line, and puts the save behaviour in each section’s header where the user can see it.

RailSticky left column with anchors in three groups: Pages (Download, Transcript, TTS, Convert, Capture), App (Console & logging, Appearance, Startup), Setup (Dependencies, Readiness, MCP access). A dot marks sections that need attention.
Form grid168 px label · control. Paths become [field][Browse]; numbers become 84 px right-aligned inputs in a two-column grid; cookie mode becomes a segment with its sub-fields indented.
Save modelEach section header states it: “Saves as you type”, “Save required” with the button in the section footer, or “Applies immediately”. Unchanged behaviour, made visible.
ScopeComposition only. Same leaf keys, same debounce and PUT paths, same readiness and MCP mutations. §05 lists all 70 test ids as keep / move / change.

03Why these moves

  • A rail turns a 2,400 px scroll into a click and gives the page a map. Grouping Pages / App / Setup mirrors how the user thinks: “the Convert page’s defaults” vs “the app” vs “is it wired up”.
  • One grid for every section lets the eye scan labels in a column and stops controls from stretching. A 60-value number in an 84 px box reads better than in a 700 px box.
  • Path + Browse on one line is the pattern used in every other page mockup; here it also halves the row count in five sections.
  • The save model is stated, not discovered. “Saves as you type” / “Save required” / “Applies immediately” costs nothing and answers the question every user asks on this page. The Save button’s dirty state and the rail dot reinforce it.
  • Diagnostics look like diagnostics. Dependencies, Readiness and MCP are lists with status chips, not forms. Readiness moves from a card of prose to a checklist with a Fix button per failing row.
  • Cookie mode as a segment with indented sub-fields makes the None/Browser/File choice and its consequences visible in one glance.

04Sizing and tokens

  • Layout: grid-template-columns: 176px minmax(0,1fr), gap 20 px, max 960 px (content ~760 px). Below ~760 px the rail becomes a horizontal scrolling chip row above the content.
  • Form grid: 168px minmax(0,1fr), row gap 9 px. All fields sm (28 px). Selects 160 px; number inputs 84 px, right-aligned, tabular-nums; path fields flex.
  • Section header: 15 px semibold title, 11.5 px bg-subtle-colored mode caption, 1 px bg-elevated rule. Dirty caption and rail dot use accent-orange.
  • Save buttons primary sm; dim (50 %) when clean; label “Save •” with btn-save-dirty when dirty. Apply defaults, Browse, Copy path, Check again, Pin token are ghost sm; Fix and Copy config are secondary sm.
  • Status chips: ok accent-green, missing accent-orange, error error; the same chip vocabulary as the queue pages.
  • Motion (G33): rail active-state and dirty-state changes on duration-fast; anchor scrolling uses scroll-behavior: smooth, disabled under prefers-reduced-motion.
  • Tokens only (G32); heights per G34.

06Decisions to lock before implementation

  1. Cookie mode control. Segment of buttons (proposed) or keep native radios styled as a segment? Tests use the -none/-browser/-file ids with click, which works either way; radios keep form semantics for free.
  2. Unify the save model? This mockup keeps three models and labels them. The alternative is autosave everywhere (drop the two Save buttons) or explicit Save everywhere. Keeping behaviour is the smallest change; unifying is a product decision.
  3. Rail active-state tracking. IntersectionObserver on scroll (proposed) or only on click? Observer is nicer; click-only is simpler to test.
  4. Number field explanations. Unit hints (“seconds”, “0 = all”) are inferred from the leaf names and the transcript service; confirm each before shipping.
  5. Boolean explanations. The one-line descriptions next to each checkbox are new copy; confirm wording or drop them and rely on the HelpCard.
  6. Audio format disabled until Audio only is checked is new behaviour (today both are always enabled). Confirm or keep both enabled.
  7. Readiness header count (“3 of 4 ready”) and the rail warn dot depend on readiness state being available at page level; confirm it already is.
