TTS page: text on the left, voice on the right, one run bar

Text-to-speech is a three-step task: paste text, pick a voice, press Generate. Today those steps are spread across a single column roughly five screens tall, with the model manager and an eleven-checkbox cleanup pipeline sitting in the middle of the path and Generate at the very end. This mockup puts the text and the voice side by side, folds the two “once in a while” groups into disclosures, and gives Generate a run bar that stays in view.

Left · TextTextarea with Load file / Paste in its header and live word · sentence · duration counts. Cleanup pipeline is a disclosure under it, closed by default, with the raw/cleaned preview inside.
Right · VoiceModel state as a chip (with “Manage” disclosure for device, load, unload, downloads). Language filter, compact voice list, speed slider with presets, format segment.
Bottom · RunOne bar: output path + Browse, Generate, Cancel, status pill, segment progress, last output with Open file / Open folder.
ScopeComposition only. Same settings leaves, same debounce, same mutations. §05 lists all 40 test ids as keep / move / change.

03Why these moves

  • Text and voice are the two inputs; they belong side by side. The user reads the text while choosing a voice, and the page becomes one screen tall at 1080p instead of five.
  • Cleanup is a preview tool, not a form. Defaults are correct for most text, so the eleven checkboxes collapse behind a toggle that states the current count. The preview panes only make sense inside that disclosure.
  • Model state is a chip; model management is a disclosure. What the user needs on every run is “is a model loaded, on which device” (the chip). Loading, downloading and unloading happen once and open on demand. With no model, the chip turns warn and the run bar says how to fix it.
  • Voices as a list, not a grid. One line per voice (id · description · language) shows twice as many voices in half the height and keeps the language filter useful.
  • Speed presets become a segment next to the slider, so the value, the slider and the shortcuts read as one control.
  • One run bar, always the same shape. Generate/Cancel and the status pill never move; the right side swaps between progress and last output. Open file / Open folder appear only when there is a file, which is also when the user wants them.

04Sizing and tokens

  • Two-column grid minmax(0,1.45fr) minmax(300px,1fr), gap 14 px, capped at ~1150 px; below ~880 px the columns stack (text first).
  • G34 heights: Generate and Cancel md (36 px); Load file, Paste, Browse, Manage, Cleanup toggle, Unload, Get/Load ghost/secondary sm (28 px). Segments 28 px.
  • Textarea: 11 rows default (~230 px), resize: vertical, bg-bg-elevated, radius 6.
  • Voice list max-height ~236 px with its own scrollbar; row 30 px; selected = 50 % accent border + 8 % fill.
  • Model chip: ok (accent-green) when loaded, warn (accent-orange) when none, live (accent, pulsing dot) while loading; status pill colors stay on STATUS_COLORS.
  • Motion (G33): disclosures and the run bar’s progress ⇄ output swap on duration-fast / ease-out; pulsing dots stop under prefers-reduced-motion.
  • Tokens only (G32); monospace counts use tabular-nums.

06Decisions to lock before implementation

  1. Format control. Segment (proposed) or keep a <select> so format-select tests keep using selectOptions? A 90 px select in the same slot is an acceptable fallback.
  2. Cleanup step labels. Humanised (“URLs & emails”) vs the raw step ids (“urls_emails”) shown today. Values sent to the API do not change either way.
  3. Loaded-model chip text. Short (“kokoro fp16 · cuda”) vs today’s full “Loaded: {variant} ({device}) · {bytes} B”. Tests currently match on the long string; bytes could move to the Manage disclosure.
  4. Open file / Open folder visibility. Render only when an output exists (proposed) or always render disabled (today)?
  5. Last output when idle. Drop “No output yet” (proposed: nothing shows) or keep it as muted text in the run bar?
  6. Voice preview. The list leaves room for a play glyph per voice; there is no preview endpoint today, so it is not drawn. Confirm it stays out of scope.
  7. Run bar stickiness. Static below the columns (proposed) or sticky at the window bottom when the page scrolls? Static is simpler; sticky only matters if the textarea is enlarged a lot.
